# [Phase 2] U-Boot 심층 분석 및 빌드 아키텍처

## 1. U-Boot가 왜 필요한가? (x86 vs ARM 임베디드 차이)

일반 PC(x86)는 메인보드에 **UEFI / BIOS**라는 표준 펌웨어가 플래시 메모리에 들어 있어, 부팅 시 하드웨어를 알아서 초기화하고 운영체제를 찾아 넘겨줍니다.

반면 **ARM Cortex-A8 (AM335x)** 같은 임베디드 SoC는:
- 부팅 직후 **DDR3 RAM이 비활성화** 상태입니다. (전기만 들어왔을 뿐 메모리 컨트롤러가 램을 읽고 쓸 줄 모릅니다.)
- 클록 속도도 최저 기본 클록(24MHz)으로 돌아가며, 전력 관리 칩(PMIC)도 초기 전압 상태입니다.
- SoC 내부에 심어진 것은 오직 수십~수백 KB의 초소형 **Boot ROM** 코드뿐입니다.

따라서 **하드웨어를 깨우고(RAM, Clock, Storage, UART 초기화), 최종적으로 리눅스 커널을 메모리에 올려 실행해 줄 전문 부트로더(U-Boot)**가 반드시 필요합니다.

---

## 2. 왜 바이너리가 2개인가? (`MLO` vs `u-boot.img`)

U-Boot를 빌드하면 산출물로 `MLO`와 `u-boot.img`라는 두 개의 핵심 파일이 나옵니다. 이 구조를 설명할 수 있어야 임베디드 리눅스의 진정한 원리를 아는 것입니다.

```text
+-------------------------------------------------------------------------------+
|  AM335x On-Chip Boot ROM                                                      |
|  - SRAM 크기 한계: 약 109 KB                                                   |
|  - DDR3 RAM: 아직 사용 불가                                                   |
+---------------------------------------+---------------------------------------+
                                        | (1) FAT32 첫 번째 섹터에서 MLO 탐색
                                        v
+-------------------------------------------------------------------------------+
|  [파일 1] MLO (SPL: Secondary Program Loader)                                 |
|  - 크기: 약 80 ~ 105 KB (109KB SRAM 내부에 딱 맞게 들어감)                    |
|  - 실행 위치: 내부 SRAM (0x402F0400)                                          |
|  - 핵심 임무:                                                                 |
|    ① PMIC(TPS65217)와 I2C 통신하여 CPU/DDR3 코어 전압 세팅                   |
|    ② PLL 클록 승압 (24MHz -> 1GHz CPU, 400MHz DDR3)                         |
|    ③ DDR3 SDRAM 컨트롤러 타이밍 파라미터 초기화 (512MB RAM 활성화!)          |
|    ④ SD 카드 / eMMC 스토리지 드라이버 로드                                    |
|    ⑤ DDR3 RAM(0x80800000)으로 'u-boot.img'를 읽어 올린 뒤 점프               |
+---------------------------------------+---------------------------------------+
                                        | (2) DDR3 RAM 활성화 후 u-boot.img 적재
                                        v
+-------------------------------------------------------------------------------+
|  [파일 2] u-boot.img (Full U-Boot Proper)                                     |
|  - 크기: 약 500 KB ~ 1 MB                                                     |
|  - 실행 위치: 외부 DDR3 RAM (0x80800000)                                      |
|  - 핵심 임무:                                                                 |
|    ① 네트워크(TFTP/NFS), 파일시스템(ext4, FAT), USB, UART 풀 드라이버 활성화   |
|    ② uEnv.txt 환경변수 읽기 및 사용자 인터랙티브 셸 (=> 프롬프트) 제공        |
|    ③ 커널(zImage)과 디바이스 트리(DTB)를 DDR3 메모리로 로딩                  |
|    ④ bootz 명령어로 CPU 모드를 커널 부팅 조건에 맞춰 변경 후 커널 진입       |
+-------------------------------------------------------------------------------+
```

### 왜 U-Boot를 한 번에 다 올리지 못하는가?
- `u-boot.img`의 용량은 수백 KB~1MB입니다.
- 하지만 DDR3 RAM을 켜기 전 SoC 내부에서 쓸 수 있는 SRAM은 **109KB**밖에 없습니다.
- 따라서 **109KB 안에 들어가는 초소형 부트로더(SPL = MLO)**가 먼저 들어가서 RAM을 켜고, 그 다음에 비로소 거대한 **풀 버전 부트로더(`u-boot.img`)**를 RAM으로 불러오는 것입니다.

## 3. `MLO` 파일의 헤더 구조 (GP Header)
AM335x Boot ROM은 아무 파일이나 실행하지 않습니다.
`MLO` 파일의 맨 앞 8바이트에는 Boot ROM이 인식하는 특수 헤더(General Purpose Header)가 들어 있습니다:
- **Byte 0~3**: 로드할 파일의 크기 (Size)
- **Byte 4~7**: 적재할 내부 SRAM 실행 주소 (`0x402F0400`)

U-Boot 빌드 시스템은 컴파일된 `u-boot-spl.bin` 앞에 이 8바이트 헤더를 붙여서 `MLO`라는 이름으로 최종 패키징합니다.

---

## 4. `u-boot.img` 파일의 구조 (Legacy uImage Header)
`mkimage` 도구를 통해 생성되는 `u-boot.img`는 순수 바이너리 앞에 64바이트 헤더가 붙어 있습니다:
- **Magic Number**: `0x27051956`
- **로드 주소**: `0x80800000` (DDR3 RAM)
- **엔트리 포인트**: `0x80800000`
- **데이터 크기 및 CRC32 체크섬**

---

## 5. U-Boot 빌드 파이프라인 (Makefile 동작 과정)

1. `make am335x_evm_defconfig`
   - `configs/am335x_evm_defconfig`를 읽어 `.config` 파일을 생성합니다.
   - BeagleBone Black, PocketBeagle, AM335x EVM 보드를 모두 아우르는 통합 설정입니다.
2. `make -j$(nproc)`
   - 1차: `spl/` 디렉터리에서 SPL 전용 소스를 컴파일하여 `MLO` 생성.
   - 2차: 루트 소스를 컴파일하여 ELF 바이너리 `u-boot` 생성 후 `mkimage`로 `u-boot.img` 패키징.
